# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A server-rendered Go web app (module `journal`), branded "Contour Journal", for mental health journaling: journal entries, action items, "thankfuls", ratings, a blog, Stripe billing, and email notifications. Built on Fiber (HTTP), GORM/Postgres (data), and `templ` (HTML templates), with HTMX-style interactions (`HX-Redirect` headers, partial re-renders).

## Product philosophy

The canonical statement of intent lives in the marketing/blog copy — `internal/web/landings/landing.templ`, `internal/web/landings/about.templ`, and `internal/blog/entries/*.md` — not in this file. Re-read those before proposing product or UX changes if unsure; this section is a summary, and the copy is source of truth.

- **The point is to process and mostly leave it, not to analyze or revisit.** Derek built this after finding that other journals either wanted him to look back and mine his own writing, or nudge him toward outcomes. This one is explicitly the opposite: write it out, optionally highlight/bookmark the rare entry worth keeping, then move on. Don't design toward "insights," AI-generated summaries/analysis of entries, or surfacing old entries back at the user unprompted.
- **No gamification, no streaks, no guilt.** Stated outright on the about page ("no streaks, no gamification... the point is to process and mostly leave it") and in the landing copy for routines ("Miss a day and it just waits. No streaks, no guilt."). Don't suggest streak counters, completion percentages framed as goals, notifications nagging about missed days, or anything that turns journaling/routines into a metric to hit.
- **Patterns/charts are optional and non-directive, not a dashboard to optimize.** "There are no specific patterns this journal is trying to show you" — the Patterns tab exists so tendencies can surface if the user wants to notice them, not to drive behavior or present KPIs. Framing suggestions around "quick stats," summary tiles, or an "at a glance" score for the Today tab cuts against this — that's product-analytics thinking, not this app's thinking.
- **Cozy over sleek.** Intentionally soft/low-contrast, not a hyper-optimized, sharp "product" feel. A suggestion that reads as conversion-rate-optimization (CTAs everywhere, urgency, engagement loops) is off-brand here.
- **Privacy is foundational, not a feature.** Encryption at rest for entries/actions/thankfuls, no ads, no tracking, no social sharing, no third-party cookies, a blur mode for writing in public. Never treat "read the user's entries" (even for a feature like AI insights) as on the table.
- **Built and used by one person, for himself first.** Derek is the primary user; the bar for a feature is "would I actually use this," not growth or engagement metrics. Paid features are an optional plan (monthly, annual, or one-time lifetime, after a 60-day no-card trial) for automation, customization, and things that cost real money to run, on top of a fully-functional free core. Export, blur mode, encryption, bookmarks, and the basic patterns are never paywalled, nothing that analyzes or resurfaces entries exists at any tier, and lapsing never costs access to the app or any data. Keep that framing in mind when weighing whether something belongs behind the plan.

## Commands

```bash
make build      # templ generate + go build -> ./main (installs templ if missing)
make run         # go run cmd/api/main.go
make watch       # live reload via air (installs air if missing); required after editing .templ files
make test        # go test ./... -v
make itest       # go test ./internal/database -v (integration test, spins up postgres via testcontainers)
make docker-run  # start dev postgres via docker-compose.dev.yml
make docker-down # stop dev postgres
make clean       # remove ./main binary
```

Run a single test: `go test ./internal/database -run TestHealth -v`

Other entry points (not in the Makefile):
- `go run cmd/migrate/migrate.go` — runs `database.RunMigrations()`, applying any pending hand-written SQL migrations (see Schema migrations below).
- `go run cmd/seed/seed.go` — **drops all tables** (including the migration tracker), re-runs all migrations, then runs seeders. Destructive; local/dev only. Refuses to run when `APP_ENV=production`. It creates one test user (`test@example.com` / `test`, `comped` so paid features stay on, email confirmed, timezone `America/Chicago`) with ~400 days of entries whose hours are drawn in that zone (so time-of-day patterns have a shape), bookmarks, two custom topics, three routines with a generated history, reminders, entry templates, action items, and thankfuls. `cmd/seed/seeders/testUser` re-seeds just that user's content without dropping tables.
- `go run cmd/stripesetup/stripesetup.go` — creates the Stripe products/prices and a customer portal configuration if missing (see Subscriptions below). Safe to re-run. Acts on whatever `STRIPE_SECRET_KEY` is set; refuses a live key unless `CONFIRM_LIVE=yes`.

Any change to a `.templ` file requires `templ generate` (done automatically by `make build`/`make watch`) before the corresponding `_templ.go` is usable — don't hand-edit `*_templ.go` files, they're generated.

Config comes from environment variables (see `.env.example`), loaded via `godotenv/autoload` from a local `.env`. Key ones: `BLUEPRINT_DB_*` (Postgres connection), `PORT`, `APP_ENV` (`production` changes GORM log level and enables the daily backup job), `CRYPTO_KEY`, `ACCESS_TOKEN_*` (JWT), `MG_*` (Mailgun), `STRIPE_*`, `R2_*`/`CF_TOKEN` (Cloudflare R2 for DB backups).

## Architecture

### Self-registering controllers
Every `internal/controllers/*.controller.go` defines a struct implementing the `Controller` interface (`internal/controllers/controller.go`): `Init(db, app)`, `RegisterViewRoutes()`, `RegisterApiRoutes()`. Each file's `init()` calls `registerController(&XController{})`. `internal/server/routes.go` iterates `controllers.GetControllers()` and calls all three methods for each — so **adding a new controller is just creating the file with an `init()` registration**; nothing else needs to be wired up.

By convention each controller owns two route groups: `views` (e.g. `/journal`, HTML pages) and `api` (e.g. `/api/journal`, JSON/mutations). View handlers typically chain fiber middleware that load data into `ctx.Locals(...)` and end with `utils.RenderPage(someTemplComponent)`; API handlers do the mutation and set `HX-Redirect` for HTMX-driven navigation instead of returning HTML.

### Locals-passing pattern
Data flows between chained handlers via Fiber locals, not return values. Set with `ctx.Locals(utils.LocalFoo, &value)`, read with the generic helper `utils.GetLocal[T](ctx, utils.LocalFoo)` (returns `*T`, logs and returns `nil` on missing/mismatched type — always nil-check). Always store pointers, and use the key constants in `internal/utils/localKeys.go` (`LocalCurrentUser`, `LocalJournal`, `LocalHasMore`, ...) rather than string literals; add a new constant there when introducing a key. The daily reminder uses its own `LocalDailyReminder` key (optional, so `reminders.DailyReminder` reads it without `GetLocal`'s missing-key warning), separate from `LocalReminder` (the one loaded by ID). `internal/web/utils.go` wraps the common ones (`CurrentUser`, `HasMore`, `NextPage`, ...) for use inside `.templ` files.

### Auth
`middleware.DeserializeToken` (global, in `routes.go`) reads the `x-token` cookie, validates the JWT (`utils.ValidateToken`), loads the `User` (with `CustomJournalTypes` preloaded) and sets `currentUser` local — but never blocks the request. `middleware.RequireAuth` is applied per-controller on route groups that need a logged-in user; it redirects to `/auth/login` if `currentUser` is unset. Because deserialization is unconditional but enforcement is opt-in per route group, a new authenticated section must explicitly add `RequireAuth`.

### Models
`internal/models/*.model.go` each `init()`-register themselves via `registerModel(...)` (`internal/models/utils.go`) — same self-registration pattern as controllers. Most models embed `*models.Base` (UUID PK, timestamps, soft delete, `CreatorID`/`LastUpdaterID`, a `jsonb` `Metadata` column) from `internal/models/base.model.go`; lookup/enum-style tables (journal types, ratings) embed `BaseType` instead (int PK + unique `Code`/`Name`). Use `models.EncodeMetadata`/`models.CastMetadata[T]` to (de)serialize the `Metadata` JSON column into typed structs. **A model's gorm tags no longer drive the live schema** (see Schema migrations below) — changing one now only affects `database.AutoMigrate()`, a dev-only convenience function that nothing in `cmd/` calls anymore; the actual schema change still has to be written as a migration.

### Views (`templ`)
`internal/web/<feature>/*.templ` mirrors the controller feature folders (`journal`, `auth`, `dashboard`, `blog`, `profile`, `actionItems`, `thankful`, `recurringActionItems`, `reminders`, `customJournalTypes`, `landings`, `components` for shared partials). Each `.templ` file has a generated `_templ.go` counterpart — edit only the `.templ` source. Page components are plain functions `func(*fiber.Ctx) templ.Component`, wired to routes via `utils.RenderPage`. Partial/fragment renders (e.g. HTMX responses that aren't a full page) use `utils.RenderComponent`/`RenderComponents` directly inside a handler.

### Patterns tab
The Patterns tab (`/dashboard?tab=patterns`) is a list of independent *patterns*, each an HTMX-loaded chart. The registry is `PatternKeys` and `allPatternDefs` in `internal/web/dashboard/dashboardPage.templ`: a key, a title, a description (the accordion copy, which is part of the product voice: warm, plain, non-directive), and the chart component. Users can hide any pattern individually (keys persist to `User.Metadata`, validated against `PatternKeys`), so a new pattern needs its key in both places. Routine completion only appears for subscribed users.

Each pattern is a `GET /dashboard/<name>` route that renders a `...Content` templ fragment, plus a JS file in `assets/js/components/` that draws it on a `load-<name>` event (always `removeEventListener` then `addEventListener`, since the fragment's script is swapped in repeatedly). Newer handlers live in their own `dashboard_<name>.go` files instead of the large `dashboard.controller.go`.

- **Pure logic goes in `internal/patterns/`**, which must never import the database or Fiber. Importing `controllers` connects to Postgres, so anything tested in the `controllers` package needs a live DB; anything in `patterns` doesn't. Handlers load rows, convert them to small structs, and call a pure function (`CountByLocalDay`, `DailyRatings`, `ComputeWeekByTime`, `ComputeRatingDistribution`, `ShareByBucket`, ...). Test helpers share one namespace across the package's test files, so prefix new ones.
- **Never load entry text for a pattern.** Select only the columns needed (e.g. `Select("date", "rating_id")` plus `Preload("Rating")`); `Journal.AfterFind` skips decryption when `is_encrypted` isn't loaded.
- **Rating colors have one implementation:** `assets/js/utils/ratingColors.js` exports `makeRatingColorizer(ratings)`, mapping the `--awful-color`..`--great-color` CSS vars onto the Rating table's sorted values. Use it (as an ES module import) rather than copying the ramp; ratings are always read from the Rating table, never hardcoded 1-5.
- **Day bucketing uses the `tz` cookie** (`time.LoadLocation`, UTC fallback) on the server; don't re-bucket in the browser with local time.
- Current patterns: the calendar (with a `lens` switch: rating / wrote / thankful / did something; the non-rating lenses pluck one timestamp column), the year in pixels (12 month rows by 31 days), rating flow, rating distribution, average rating by topic, the week-by-time-of-day heatmap (cells with fewer than 3 entries are drawn fainter), the two "rating vs thankfulness / action completion" comparisons (each group's *share* of days per rating, so unequal group sizes stay comparable), topic distribution, and routine completion (a count of times done, never a percent). Per-day entry and thankful counts live in the calendar's lenses, and average rating by weekday / time of day live in the heatmap; the standalone charts for those were retired, so don't re-add them.
- Spirit when adding or changing a pattern: no streaks, goal lines, "best/worst" callouts, summary tiles, or sentences that interpret the data for the user; empty days are plain blank with no "missed" styling; show sparse data honestly (fainter, not warned). See the findings in `docs/patterns-dashboard-findings.md`.

### Offline drafts (write now, sync later)
New-entry autosave is local-first. `assets/js/journal/autosave.js` writes the form to `localStorage` on every input (`assets/js/utils/drafts.js`), then saves to the server as before; a draft is deleted only once the server confirms that exact text. Offline, a server error, or an expired session leaves the draft in place, and `flushDrafts()` retries it on reconnect, tab focus, page load, and a 30s timer while the page is open. Only **new** entries are drafted — an existing entry saves straight to the server, because replaying an offline edit over a copy changed elsewhere would silently overwrite it.

Each new entry's form carries a client-generated `draftId` (hidden input). `createJournal` stores it in the journal's `Metadata` (`models.JournalMetadata`) and, if it has already seen that id for this user, treats the request as an update — so a retry after a lost response can't create a second entry.

`assets/sw.js` is the service worker, served from `/sw.js` (not under `/assets/`, whose path would cap its scope) with `AssetVersion` stamped in by `web.ServiceWorkerSource`. It caches only the static assets and the `/journal/new` page — never the dashboard, list, or entry pages, which hold decrypted entries — and serves that cached page offline for `/journal/new` and `/dashboard` (the PWA's `start_url`). `assets/js/utils/offline.js` registers it, hands it the page's own `/assets/` resource list to cache, and on logout flushes any pending drafts, warns if some can't sync, then wipes drafts and the worker's caches. Drafts are plaintext on the device (no server-side encryption applies there), which is why they are removed the instant they sync and wiped at logout.

### Native app shell (`mobile/`)
A thin Capacitor project that opens the live site in a webview (`server.url` from `CONTOUR_URL`); it bundles none of the web app, so a server deploy updates it. It appends `ContourApp/1.0` to the webview's user agent, and `middleware.DetectNativeApp` (global, after `FilterBots`) turns that into `LocalIsNativeApp`, read in templates via `web.IsNativeApp(c)`. For the shell only: `/` redirects to `/dashboard` (`middleware.NativeAppHome`), the footer drops About and Blog, and the profile plan section drops the checkout/portal buttons (store rules restrict selling plans in-app; people subscribe on the web). The user agent is client-controlled, so this is presentation, never enforcement: the billing API routes are not blocked. Safe areas: for the shell, `base.templ` adds `viewport-fit=cover` and `data-native-app` on `<html>`, and the header, footer, hamburger and slide-out menu pad themselves by `env(safe-area-inset-*)` so the page draws under the status bar and its own theme color fills it (a native-side margin can't follow the light/dark toggle). `theme.js` (`applyNativeStatusBar`) sets the StatusBar plugin's icon style to match the page theme, registering the plugin by name because a server-loaded page has no bundled plugin imports. Setup and device checks are in `mobile/README.md`.

### Background jobs
`internal/jobs/jobs.job.go` runs a `gocron` scheduler, started by `jobs.Start()` (called explicitly from `cmd/api/main.go`; importing the package starts nothing, so tests can import it). The package and `internal/middleware` reach the database through a lazy `DB()` (connects on first use); tests point them at a test database with `SetDB` polling every 10s for due `models.Job` rows (`processed_at IS NULL`, `scheduled_at <= now`, under the retry limit) and dispatching by `job.Type` (currently only `EMAIL_JOB_TYPE`). To add a new async job type: create a `<name>.job.go` with a `Schedule<Name>Job(...)` constructor that saves a `models.Job` with typed `Metadata`, add a `case` in `runJobs`'s switch, and a handler function that decodes the metadata via `models.CastMetadata[T]`.

Backups (`internal/database/backup.go`) are a separate `gocron` job (own `init()`), production-only, running daily: `pg_dump` → upload to Cloudflare R2 → prune old backups per a retention policy (all backups kept 30 days, then thinned to weekly up to 6 months, then monthly beyond that).

### Request log (anonymous by design)
`middleware.LogAccess` (global, `routes.go`) writes one `models.Analytic` row per request: time, method, host, path, response status. It deliberately records **no** IP, user agent, query string, or account ID (`CreatorID` is always `uuid.Nil`), so it can't be a per-person history; migration 000010 dropped those columns and deleted the old rows. `jobs.pruneRequestLog` hard-deletes rows older than `models.RequestLogRetention` (14 days). Each request also gets a random 8-hex reference (`middleware.RequestID`, outermost middleware; sent as `X-Request-ID`, stored in `analytics.request_id`, never derived from or shared across anything about a person, and any client-supplied value is ignored). It's the debug handle: 5xx responses with a plain-text body get `(reference: <id>)` appended, the htmx failure dialog (`handleHtmxError` in `utils/index.js`) shows it for JSON errors too, and `LogAccess` writes a `request failed` log line with the id, path, status and a sanitized cause on any 5xx. The cause comes from `utils.SetRequestError(ctx, err)`, called right before a controller returns a 5xx; `utils.ErrorCause` deliberately logs only Postgres code/table/constraint, a few safe sentinel errors, or the Go type, never raw error text (DB errors quote values, e.g. an email). There is intentionally no session ID: it would string a person's requests together. Tests (`middleware/logAccess_test.go`, `middleware/requestID_test.go`, `utils/requestError_test.go`, `jobs/requestLog.job_test.go`) fail if an identifying field or column comes back. The privacy policy (`internal/web/landings/privacy.templ`) states all of this, so change them together.

### Database layer
`internal/database/database.go`'s `Service`/`New()` is a process-wide singleton (`dbInstance`) built from `BLUEPRINT_DB_*` env vars; `middleware.go` and `jobs.job.go` each independently call `database.New()` to get the same instance rather than receiving it via DI. GORM is configured with `time.Local = time.UTC` (set in `server.New()`) and `NowFunc` pinned to UTC — timestamps should be treated as UTC throughout; per-user timezone handling (see `journal.controller.go`'s date filtering) is done explicitly with the `tz` cookie and `time.LoadLocation`.

`internal/database/database_test.go` is an integration test using `testcontainers-go` to spin up a real Postgres — this is what `make itest` runs; it mutates the package-level connection vars, so it must stay in the `database` package's own test binary.

### Schema migrations
Schema is owned entirely by hand-written SQL migrations in `internal/database/migrations/`, applied by `database.RunMigrations()` (`internal/database/migrate.go`) — a small hand-rolled runner (no third-party migration library; an earlier attempt with `golang-migrate` was reverted because its `postgres` driver package pulls in a large, disproportionate dependency tree — Docker SDK, containerd, gRPC, OpenTelemetry — just to run some SQL). Pending `.up.sql` files are applied in filename order, each in its own transaction, tracked by version in a `schema_migrations` table. `000000_initial_schema.up.sql` is the baseline — a full schema-only dump of every table/index/constraint, with every statement written as `CREATE TABLE/INDEX IF NOT EXISTS` (or constraints inlined into the `CREATE TABLE` itself, since Postgres has no `ADD CONSTRAINT IF NOT EXISTS`) so it's a safe no-op replay against a database that already has the tables — this is what makes it safe for both a genuinely fresh install and an already-existing (dev/prod) database. Every migration after the baseline should follow the same idempotent-guard convention. Migration files are plain numbered SQL (`NNNNNN_description.up.sql`); there's no CLI/codegen for scaffolding new ones — copy the naming convention by hand. `.down.sql` files are written alongside for documentation/manual rollback but aren't auto-applied by anything. `GORM`'s `AutoMigrate()` still exists (`internal/database/database.go`) but nothing in `cmd/` calls it anymore — it's a dev-time convenience for quickly trying a model change locally before writing the real migration, and staying in sync with it (verify with a throwaway DB, as done when this baseline was built) is worth checking after a schema change lands. `cmd/seed/seed.go`'s `DropTables()` also drops `schema_migrations` itself, so a full reseed re-runs every migration from scratch rather than skipping them as "already applied" against tables that no longer exist.

### Subscriptions
The app uses a subscription (plan and rollout: `docs/subscription-plan.md`) instead of per-feature purchases. Paid features are gated on `User.IsSubscribed()`: use `middleware.RequireSubscription` on API routes and `IsSubscribed()` in templates. The old `Feature`/`UserFeature` tables and models still exist but nothing reads them (`HasFeature`/`RequireFeature` are gone); a later migration drops them. Gating rule: **creating** a paid thing needs an active plan, while **editing, deleting, and viewing** what already exists never does (custom topics, routines). Routines created by the once-a-minute cron skip any owner who isn't subscribed, so they wait and resume with the plan (`RecurringActionItemController.subscribedCreators`). `web.GraceBanner` (in `base.templ`) shows one dismissible note during the 14-day grace period.

- **State on `User`** (migration `000004_subscriptions`): `SubscriptionStatus` (`trialing`, `active`, `past_due`, `canceled`, `lifetime`, `comped`), `TrialEndsAt`, `CurrentPeriodEnd`, `StripeSubscriptionID`, plus the existing `StripeCustomerID`. Constants and logic live in `internal/models/subscription.go`.
- **Trial and grace:** a new account gets a 60-day trial with no card, started in `User.BeforeCreate` (`startTrial`, which leaves an explicitly-set status alone). After a trial or paid period ends there's a 14-day grace period where paid features still work. `IsSubscribed()` is the single entitlement check (lifetime/comped always true; others true until end + grace; `active`/`past_due` with no known period end count as subscribed); `InGracePeriod()` is true between the end and end + grace; `AccessEndsAt()` is `TrialEndsAt` for a trial, `CurrentPeriodEnd` for active/past_due/canceled, else nil. Lapsing never deletes anything.
- **Plans** are resolved by Stripe lookup key (`contour_monthly`, `contour_annual`, `contour_lifetime`), not env price IDs, via `internal/stripe/stripe.go` (`ParsePlan`, `GetPlanPrice`). `cmd/stripesetup` creates them. Monthly/annual use Checkout subscription mode; lifetime uses payment mode.
- **Routes** (`profile.controller.go`, under `/api/profile/billing`): `POST /checkout/:plan` (lazily creates the Stripe customer via `ensureStripeCustomer`, sets `client_reference_id` to the user ID, redirects via `HX-Redirect`; refuses lifetime/comped/active/past_due users) and `POST /portal` (Stripe customer portal to manage/cancel). The profile page's plan section drives both.
- **Webhook** (`stripe.controller.go`, `/api/stripe/webhook`) handles `checkout.session.completed` (links the subscription ID, or marks lifetime on a paid payment-mode session and cancels any recurring subscription) and `customer.subscription.created/updated/deleted` (maps Stripe status to ours and sets `CurrentPeriodEnd`, via the pure `stripe.SubscriptionState` in `internal/stripe/subscription.go`, kept out of `controllers` because importing that package connects to Postgres, so tests there need a live DB). `past_due` arrives via `subscription.updated`, so `invoice.payment_failed` isn't needed. Handlers are idempotent since Stripe can redeliver and reorder events; events for a subscription ID other than the user's current one are ignored. **Lifetime and comped accounts ignore subscription events.** Stripe's current API puts the period end on the subscription *items* (`items.data[].current_period_end`), not the subscription, so that's where it's read from.
- **Themes (paid):** `users.theme`/`font_family` (`''` = default; allowlists in `models/appearance.go`, which must match `css/theme/appearance.css`). `base.templ` renders `data-palette`/`data-font` on `<html>` only when `IsSubscribed()`, so a lapsed user sees the default and their saved choice is kept. A palette changes only the primary tints and the accent (via `--palette-hue`), with light and dark variants. `theme.js` mirrors the choice to `localStorage['appearance']` and prefers it when offline (the service worker's cached `/journal/new` can predate the latest choice). Saves go to `PUT /api/profile/appearance` behind `RequireSubscription`. The existing `data-theme` attribute is light/dark, not palette.
- **Entry templates (paid):** user-authored `models.EntryTemplate` (name and body encrypted at rest like reminders; table `entry_templates`). Managed at `/entry-templates` (the profile links to it). Listing and deleting stay open to lapsed users; create, update, the edit form, and the picker JSON (`GET /api/entry-templates`, sent `no-store`) need `RequireSubscription`. The new-entry picker is fetched at runtime by `journal/templatePicker.js`, never embedded in the cached `/journal/new` page, and prefills through the normal `input` event so offline-draft autosave applies.
- **Reminder email (paid):** `users.timezone`/`reminder_email_*` (migration 000007). `jobs.scheduleDueReminderEmails` runs every 3 minutes and calls the pure, tested `models.ReminderEmailDue`. `queueReminderEmail` claims the user's local day with a conditional UPDATE of `reminder_email_last_sent_on` in the same transaction as the email job, so a race or restart can't double-send. The timezone is captured from the `tz` cookie when settings are saved. The email is a short default line (or the user's own message, encrypted at rest via `User.SetReminderEmailMessage` and never stored in the job row; it's decrypted at send time) plus a link. The user's actual reminder text is never emailed. At send time the job is skipped if the user has since turned it off or lapsed. No catch-up or missed-day logic. Turning it off stays allowed for lapsed users. Needs `ROOT_URL` set.
- **Email confirmation** (migration 000008): `users.email_confirmed_at` / `email_confirmation_sent_at`. It never gates the app; it only gates email nobody asked for in the moment, which today is the reminder email (enabling it returns 403 until confirmed; the scheduler query and the send-time check in `prepareReminderEmail` also require it). Password reset and other transactional mail are unaffected. Signup queues the confirmation email (best effort); the profile's Reminder Email card shows "Send confirmation email" (`POST /api/profile/confirm-email`, throttled to one a minute). The link (`GET /auth/confirm-email?token=`, no login needed) carries a 48h JWT from `utils.CreateEmailConfirmToken`, which has no `sub` claim so it can't work as a login cookie, and is bound to the address it was issued for. The migration backfills existing users as confirmed, only when the column is first added. There is no email-change feature yet; when one is added, clear `email_confirmed_at` and resend.
- **Routine email (paid, per routine):** `recurring_action_items.email_me` (migration 000009), set by the "Email me when this comes up" checkbox on the routine form. When the once-a-minute cron creates an action item from such a routine, `emailRoutineOwners` queues one short generic email (a `GENERAL` email job) per owner, only to a confirmed address. Like the daily reminder it never contains the routine's text, since jobs are stored unencrypted. Routines of lapsed owners are already skipped by the cron, so no email goes out for them either.
- **Plan copy:** the about page, the "Cost" section of `internal/blog/entries/what-is-contour-journal.md`, and the profile plan section state the pricing ($3/month, $24/year, $48 lifetime; 60-day no-card trial) as the current model. Update them together if prices or the feature list change.
- **Comping an account** is a manual `UPDATE users SET subscription_status = 'comped' WHERE email = '...'`.

## How Derek works

- **Deploys and branch cleanup are gated on an explicit go-ahead.** Never merge, push to a shared/deploy branch, or deploy just because a build/test run passed — wait for an explicit "merge and deploy" (or equivalent). Same for deleting a branch after a merge: wait to be told, don't do it automatically as cleanup.
- **Small/doc-only changes can skip branch ceremony** (commit straight to the working branch) but still only on an explicit ask to commit/push — same gating as bigger changes, just less process around it.
- **Never touch Derek's own local dev server** — treat a running `make run`/`make watch` process as his, not something to start, stop, or curl on his own behalf.
- **Production is reachable via `ssh debian`** (an SSH config host alias), repo checked out at `~/sites/journal` on that host. Postgres runs natively on that host (not containerized); the app runs there via `docker compose` with `network_mode: host`, fronted by nginx proxying to `127.0.0.1:$PORT`. There's no CI/CD and no deploy script in-repo — a deploy is whatever manual sequence (`git pull`, `docker compose up -d --build`, running `cmd/migrate`, etc.) makes sense on that host. Still gated on the same explicit go-ahead as any other deploy. The host has no Go toolchain and the app image doesn't ship `cmd/migrate`, so migrations run in a throwaway container on the host network, before restarting the app: `docker run --rm --network host -v "$PWD":/src -w /src golang:1.24-alpine go run cmd/migrate/migrate.go` (from `~/sites/journal`; it picks up `.env` from the mounted repo). Migrations aren't run on app startup. Plain `curl` gets a 403 from the bot filter, so use a browser User-Agent when smoke-testing `127.0.0.1:$PORT`.
- **Never print a real `.env` file** (`cat`/`tail`/etc.) — it's a live secrets file, and doing so leaks every value into the transcript, not just the one being checked. To confirm which keys exist without exposing values, `grep -o '^[A-Z_]*=' .env`; to check whether a specific key has a value set, `grep -c '^KEY_NAME=.\+$' .env`. Appending new keys is fine without reading the file first.
- **Verify uncertain external-system behavior live rather than trusting docs or assumptions** — when unsure what a third-party API/service (Stripe, Mailgun, R2, etc.) actually does, confirm it against the real thing (a dev/test account, never live production data) rather than guessing from documentation, which has been wrong before.
- **Docs drift is part of finishing the change, not a follow-up.** If a change affects something this file, a README, or another doc describes, update that doc in the same change rather than leaving it to go stale.
- **Testing style**: prefers small helper constructors (e.g. a `fooItem`/`barItem` builder function) over fixture files or mocking frameworks — match whatever convention already exists in the file/package being touched.
- **Elephant and goldfish workflow** (use where applicable, i.e. work that splits into self-contained pieces). The *elephant* is the main session: it keeps the whole conversation, reads the code, makes the decisions, and writes a complete, self-contained spec per piece (goal, exact files to touch and not touch, existing patterns to match, constraints from this file, how to verify, what not to do). Each *goldfish* is a cold subagent that remembers nothing, so it builds only from its spec, in its own worktree (`isolation: "worktree"`), and reports back what it changed and what it couldn't verify. The elephant then reviews each diff against the spec, resolves overlaps between pieces, merges, and runs the build/tests. Goldfish never decide product questions, commit, push, merge, or deploy, and never touch secrets or the dev server. If a spec can't be written without back-and-forth, it isn't goldfish work; keep it with the elephant.
- **Agent delegation is deliberate, not a blanket default.** Different phases call for different tools: read-only reconnaissance ("where does X live," "what's the existing pattern for Y") suits a fast search-only agent; turning an open-ended problem into a concrete spec suits a planning agent; a fully-specified, self-contained task suits a worktree-isolated execution agent. Keep anything needing iterative back-and-forth (debugging against screenshots/live feedback, "still broken, try this" loops), git workflow, small edits, and anything touching secrets or requiring live verification against an external API direct rather than delegated — worth doing visibly himself even when small.
